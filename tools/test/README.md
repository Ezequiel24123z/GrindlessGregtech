# Test bench (home PC)

It uploads `pack/` (plus `tools/test/overlay/`) to the home PC, starts a **clean** server or client (new world, no previous state) and returns logs and a PASS/FAIL summary. All the heavy work runs there, in `D:\GregtechGrindless`; here it is only launched and read.

## How to run it

Implement and integrate all changes for a tier before its **single coordinated validation run**. One agent/session owns the complete candidate, schedules any necessary stages serially and collects the result; feature authors do not launch separate clients or servers. Include pending cross-cutting improvements in the same batch. Small, low-risk changes need no additional test unless there is a concrete failure risk or known regression; reuse valid existing proof. The examples below describe individual checks, not a requirement to run each in a fresh JVM.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\test\Invoke-GGTest.ps1 -Suite server `
  -Commands 'kubejs custom_command gg_ping' -WaitForLog 'GGTEST\|PING\|PASS'
```

| Suite | What it does | Success |
|---|---|---|
| `server` | Dedicated Forge (normal world, fixed seed): starts until `Done`, runs `-Commands` over RCON, waits for the `-WaitForLog` patterns, stops with `stop`. | It starts, the commands respond, the markers appear, clean shutdown. |
| `client` | HeadlessMC + mc-runtime-test: creates a world with one player and exits. The client is the pack's **real** client (Embeddium, ImmediatelyFast, …) with software OpenGL (see "Client without GPU"). | Exit code 0, `Successfully finished.`, no crash report. |
| `both` | Server and then client (one slot on the PC). | Both. |

Useful parameters (all optional):

- `-Commands 'cmd1;;cmd2'`: RCON commands, in order, or `-CommandsFile` (one per line). **With `-File`, PowerShell does not split lists on commas: use `;;`.**
- `@restart`, or `@restart:<regex>` with more markers joined by `&&`, as one of the `-Commands` (the server stage of `-Suite server` or `both`, at most one per run) is not sent over RCON: the bench restarts the server once, for a test that needs a cold start of the same world (persistent data, chunks and machines read back from disk). It waits until every marker has appeared in `logs\kubejs\server.log` or `latest.log` (at most 180 s or `-WaitTimeoutSec`, whichever is lower), stops the server through its console (`stop`, the shutdown's 30-second grace, exit code 0 required: the world and persistent data saved), moves the first boot's logs to `results\server\phase1\` and starts the same command line (same heap) on the same world, with the same boot, settle and RCON stages. The run keeps its slot and the global mutex the whole time, so it is still the one test JVM, and every wait spends the run's one native budget (never reset). The restart ends every test still running, and nothing a test keeps in `global` survives it: in a run with other tests, put it after their commands and list their `DONE` markers with `&&`. `-WaitForLog` markers may come from either boot. The summary counts the `GGTEST` lines of both boots; `kubejs-errors-phase1` checks the first boot's KubeJS logs.
- `-WaitForLog 'regex1;;regex2@@90'`: expressions that must appear in `logs\kubejs\server.log` or `latest.log` (the `@@90` sets their deadline in seconds; default `-WaitTimeoutSec 120`, maximum 180 per marker).
- `-Flat` flat world; `-Seed`; `-ServerXms/-ServerXmx` and `-ClientXms/-ClientXmx` (1G/4G each, maximum heap 4 GB); `-ServerProp 'difficulty=peaceful'`.
- `-BootTimeoutSec` (420), `-ClientTimeoutSec` (600), `-CommandTimeoutSec` (60): defaults are also the maximums. `-NativeTimeoutSec` (600 maximum) is a shared deadline from the first Minecraft launch, not a fresh allowance per stage/suite. Server shutdown has a separate 30-second grace. `-LockWaitMin` defaults to 5 (maximum 15).
- `-SettleSec` (15): after `Done`, the server waits at least this long before RCON/`-Commands`, and longer while a datapack reload is in progress (e.g. the one that Additional Placements triggers ~2 s after `Done` and that restarts the KubeJS scripts). Its own stage `settle` (`results\server\settle.txt` lists what was detected); `0` disables it. If a reload starts later than the minimum, raise it.
- `-Slots 1` is mandatory: one Minecraft JVM globally. Available RAM is not a launch condition. Legacy `-SlotMinFreeGb` arguments remain accepted with a deprecation warning and are ignored; new upload requests omit that field (see "The home PC").
- `-ClientRenderer mesa|stub` (default `mesa`) and `-ClientExclude 'regex;;regex'` (only useful with `stub`; see below).
- `-Strict` also fails on WARN stages, ERROR lines that are not allowed, or KubeJS errors.
- `-SkipRefresh` (only if the index is already fresh: the bench checks this before uploading and warns if it is not), `-PackDir`, `-OverlayDir`, `-OutDir`, `-ShowWarnings`.
- There is no `-KeepServerRunning`: the server always stops when it finishes.

Before uploading, `tools\Update-PackIndex.ps1` sets the text files in `pack/` to UTF-8 without BOM and LF, and runs `packwiz refresh`.

Examples below use the current bounded deadlines; they are not permission to rerun an unchanged proof. Consolidate necessary checks into the tier's integrated candidate. If it cannot finish within those limits, report the unresolved coverage rather than silently extending the budget or retrying automatically.

## Client without GPU or window

The home PC is driven over SSH (Windows session 0: no monitor and no desktop), and HeadlessMC's `-lwjgl` is a stub whose `glFenceSync` returns 0, which crashes Embeddium (`Failed to create fence object`, with no config option). That is why the default mode (`-ClientRenderer mesa`) uses **real OpenGL on the CPU** and does not touch the mod set:

- **Mesa llvmpipe** (pal1000/mesa-dist-win 26.2.4): Mesa's `opengl32.dll` next to `java.exe` in a **private copy** of JDK 17 (`D:\GregtechGrindless\tools\jdk17-mesa`; the system JDK is not modified) and `GALLIUM_DRIVER=llvmpipe`. It provides OpenGL 4.6 without a GPU. The bench checks that the game JVM loaded Mesa's `opengl32.dll`/`libgallium_wgl.dll` (`Mesa llvmpipe GL confirmed` in the `client-launch` stage), and the overlay logs `GGTEST|CLIENT-GL|renderer=…`.
- **Real LWJGL**: HeadlessMC turns on its stub when it runs with `--offline` and an "offline" account; a fake account from another provider in `hmc\home-mesa\.auth` avoids it (the game only logs an authentication 401, which is in the allowlist).
- **No monitor**: `earlyWindowControl = false` is set in `config\fml.toml` for the test client only (Forge's startup window aborts without a monitor).
- **"Experimental Settings" warning**: because the pack ships worldgen data, Minecraft asks when a world is created, and mc-runtime-test cannot answer. `overlay/kubejs/startup_scripts/gg_test_client.js` presses "Yes" (a Forge tick event; KubeJS's `ClientEvents.tick` does not fire without a world).
- To keep it light, `renderDistance:4`, `simulationDistance:5` and `maxFps:30` are forced. A timeout stops the owned process tree promptly and collects existing logs; it does not prolong the run to collect live JVM diagnostics.

`-ClientRenderer stub` (HeadlessMC `-lwjgl`, no OpenGL) **does not work for this pack**; it is only kept as a plan B for small packs. Tested with the real client: the stub first takes down Embeddium (`Failed to create fence object`, it has no config option), then ModernFix (`StbStitcher`: `Struct cannot be cast to STBRPRect`) and then GTM's LDLib (`GL Shader Allocation Fail!`); removing all of them is no longer "the real client". By default the stub removes only Embeddium (`-ClientExclude '^embeddium[-_+0-9]'`; `-ClientExclude none` to remove nothing). `pack/` is never touched.

## Result

Output goes to the console and is saved in `-OutDir` (by default `…\files\test-runs\<date>-<suite>\`):

- `summary.txt` / `summary.json`: stages with status and duration, `GGTEST|` lines, crash reports (with the cause), KubeJS errors, and `ERROR` lines that are not in `log-allowlist.txt`.
- `results\server\` and `results\client\`: `logs\latest.log`, `debug.log`, `logs\kubejs\*.log`, `crash-reports\`, `hs_err\`, `kubejs-exported\` (whatever a test writes to `kubejs/exported/`), `mods.txt`, `rcon.log`, `settle.txt` (server); on the client also `client-hmc-stdout.log`. Note: HeadlessMC kills the game as soon as a crash report appears, so the folder may come out empty (the cause is then taken from the log).
- Exit code: `0` PASS, `1` FAIL, `2` failure of the bench itself (no results).

FAIL if a stage fails, there is a crash report, or a `GGTEST|…|FAIL` line appears. `WARN` stages (KubeJS errors, forced stop) do not fail unless `-Strict` is used.

## Writing a test (overlay)

Scripts in `tools/test/overlay/` are copied **on top of** the instance on the home PC and never go into the pack. Besides the tests, the overlay carries `config/voicechat/voicechat-server.properties` (`port=-1`): Simple Voice Chat uses the server's game port rather than assuming its default UDP 24454 is free. Example (`overlay/kubejs/server_scripts/gg_test_harness.js`):

```js
ServerEvents.customCommand('gg_ping', event => { console.info('GGTEST|PING|PASS'); return 1 })
```

It is run with `-Commands 'kubejs custom_command gg_ping'`. Output convention: `GGTEST|<suite>|<check>|PASS` or `|FAIL (detail)`; the summary counts them, and any `FAIL` makes the run fail. `GGTEST|READY` is printed when the server loads. The overlay also applies to the client (`startup_scripts/gg_test_client.js` and `client_scripts/gg_test_client.js` go there).

Tip for KubeJS 6.5 (Rhino), observed here: inside event handlers, `const`/`let` can throw `redeclaration of var X`; use `var` and `function () {}`. Also, KubeJS's `ClientEvents.tick` only fires when a world and player are loaded.

Vanilla names in KubeJS 2001.6.5: its mixins (`@RemapForJS`) rename some members for the scripts, and the Mojang name **does not exist** (nor the SRG name): `Entity#getYRot/getXRot` → `getYaw/getPitch`, `getUUID/getStringUUID` → `getUuid/getStringUuid`, `tickCount` → `age`, `Level#getGameTime` → `getTime`, `Level#dimension()` → `getDimensionKey`, `Player#closeContainer` → `closeMenu`, `Direction#getStepX/Y/Z` → `getX/Y/Z`, `ItemStack#getTag` → `getNbt`; `Entity#level()` is hidden (use `getLevel()`). The full list is in the KubeJS and Rhino mixins (`EntityMixin`, `LevelMixin`, `ItemStackMixin`, `DirectionMixin`…). The `server` suite has no player: code that uses one is tested in the `client` suite.

`gg_test_recipe_lookup` (`server` suite) asks GTM's own recipe lookup (`RecipeDB#find`) for every GT recipe with that recipe's own inputs: GTM 7.5.3 keeps one recipe per ingredient path, so a recipe that another one shadows can never run in a machine (EMI still shows it). Any unreachable recipe not in the test's baseline of accepted addon-vs-addon conflicts fails, and so does one of ours (a `grindless:` id or a recipe our scripts add or change) on either side: `-Commands 'kubejs custom_command gg_test_recipe_lookup' -WaitForLog 'GGTEST\|lookup\|DONE@@180'`. The addon collisions that lose a route are fixed by the pack (`integration/lookup_collisions.js`, table `lookup_collisions.json`); the test checks those recipes by name. Before `DONE` it writes the unreachable recipes to `kubejs/exported/lookup_unreachable.json`: run it with `gg_dump` and `tools/analysis` drops them from its model (it prints how many).

The wireless energy network (`server` suite, band X 13312–13375, Z 0–63, the Overworld at Y 98–112 and the Moon at Y 198–214; the End's chunks of that band only as unloaded metadata, no blocks): `gg_test_wireless_energy` is the whole network in one boot (towers, hatches, covers, unloading, the save). `gg_test_wireless_adapters` checks how EU goes into and out of GTM's item machines (chargers and battery buffers: the items' real charge, the store and the rate per settlement; the converter refused; an old-format list converted). `gg_test_wireless_restart_1` / `_2` go around a `@restart`: the list (with 1,200 synthetic entries in unloaded chunks, past what the old single string could save), the store and the endpoints across a cold start, with nothing placed or clicked again. Phase 1 waits for `gg_test_wireless_adapters` when both run. Both scripts also run in a simulated server in `tools/analysis/test/wireless_network.test.mjs`. In a run of their own they would be `-Commands 'kubejs custom_command gg_test_wireless_adapters;;kubejs custom_command gg_test_wireless_restart_1;;@restart:GGTEST\|wireless_restart\|PHASE1\|DONE;;kubejs custom_command gg_test_wireless_restart_2' -WaitForLog 'GGTEST\|wireless_restart\|DONE@@180'`; in an integrated run, the restart goes last, with the other tests' `DONE` markers added to its own.

## The home PC

- It only writes to `D:\GregtechGrindless` (`tools`, `cache`, `sync`, `hmc`, `incoming`, `runs`). Never to PrismLauncher, `D:\Grindless` or `.minecraft`.
- **One Minecraft test JVM globally**, across all agents and worktrees. The scheduler's hard ceiling is one, even if a legacy caller asks for more. A process-held `Global\GGHarness-minecraft` mutex excludes other updated runners even if metadata disappears; it is released only after owned processes stop. Runs also use `runs\.lock` (PID/acquisition time and a 30-second heartbeat); old nonzero slot files still block new work. FIFO waiting polls every 15 seconds, normally for at most 5 minutes. One owner coordinates the tier's integrated run rather than enqueueing independent feature runs; `both` can provide required serial server/client stages under the same budget. Older lock files' `started` field recorded queue entry, **not acquisition**; do not infer concurrent JVMs from that timestamp alone.
- **Heap, without a RAM floor:** both sides use `-Xms1G -Xmx4G`. The 4 GB limit is Java heap, **not total RSS**: metaspace, native libraries, Mesa and launcher memory are additional. Available/free RAM and unreadable memory counters do not refuse launch; the user explicitly removed that preflight restriction. Legacy `SlotMinFreeGb` values must not reintroduce it. Requests that exceed the unchanged heap/deadline limits still fail explicitly before launching; do not silently raise them or retry after an out-of-memory failure.
- **Integrated, bounded runs:** identify the unresolved mechanisms and regressions covered by the complete candidate; run necessary source/static checks locally and reuse existing proofs. The total native budget remains at most 10 minutes from the first JVM launch (startup included and shared by all stages); server clean shutdown gets at most 30 seconds before its owned tree is killed. RCON operations share one absolute deadline across fragmented replies. Boot, commands and marker waits also have the shorter limits above. These are hang safeguards, not target durations. Increasing the budget requires the user's approval and a deliberate policy change; no old launch scripts, manual JVMs or automatic restart chains to bypass it (the one `@restart` a server run may hold spends the same budget and the same JVM lease). After a demonstrated failure, fix and rerun only the affected check under the same validation owner.
- **Orphans**: only JVMs from runs whose slot has expired are killed (the server carries `-Dgg.run=<id>` on its command line; the client and packwiz-installer carry `runs\<id>\`). Never the JVM of another active slot, nor unrelated processes (PrismLauncher, `D:\Grindless`). Shared resources (downloads into `tools\`, Forge installation, the `sync\<pack>-<side>` directory and its copy) are protected with a system mutex; the client in slot N>0 uses its own `hmc\slotN\` (HeadlessMC's config and `.minecraft`; the first time, it installs Forge again). Any manual experiment that uses a JVM must take a slot and keep a short time limit.
- Caches: Forge per version (`cache\forge-server`), mods per pack and side (`sync\`; packwiz-installer downloads them once), HeadlessMC's client (`hmc\`), Mesa and its private JDK (`tools\mesa`, `tools\jdk17-mesa`). Each run copies what was synced to `runs\<id>\`; the last 3 are kept.
- A CurseForge mod that does not allow distribution makes `sync-*` fail: put its jar in `D:\GregtechGrindless\cache\manual-mods\`.
- The remote scripts (`tools/test/remote/*.ps1`) are copied to `tools\remote\<hash>\` only if missing: they are uploaded to a temporary folder, which is then renamed, so the final folder is always complete even when several runs upload at the same time.
