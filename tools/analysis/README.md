# Static progression validator

Checks, tier by tier and **with no commands**, three things about the pack as it's actually loaded (final recipes after the scripts run):

1. **Gate** (step 1): the gate to the next tier can be built. Hand-gathering what's in the world is allowed.
2. **Auto** (step 2): base resources are resupplied by machines (vein drill, greenhouse, pump, fluid rig, rock crusher...), not by hand. Only what's gathered by hand once to bootstrap counts.
3. **Eras** (step 3, decision of 2026-10-24): nothing from an era can need a resource that comes from a later era. Every era's item has to be buildable with **every** later-era resource removed from every source (veins, byproducts, bees, addon recipes, other dimensions).

Separately, a step that doesn't belong to any tier: the **obtain audit** (`--pass obtain`, see [below](#obtain-audit---pass-obtain)) lists what is never obtained anywhere in the pack and classifies it.

## How to run it

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\analysis\Invoke-Reachability.ps1 -Tier iv   # steam | lv | mv | hv | ev | iv (or next/<tier>: prepared layer; none exists today)
```

One single command: uploads `pack\` and a minimal overlay (just `gg_dump.js`) to the home PC with `tools\test\Invoke-GGTest.ps1`, starts a clean server, runs `kubejs custom_command gg_dump`, retrieves `kubejs\exported\*.json`, and runs `reachability.mjs` with Node. Takes 2-8 min (longer if the PC is busy: only one JVM at a time). The report prints to the console and goes to `tools\analysis\out\<date>-<tier>\report-<tier>.txt/.json`. Exit code: `0` PASS, `1` FAIL/WARN, `2` tool failure.

| Option | Effect |
|---|---|
| `-SkipDump [-DumpDir <folder>]` | doesn't start the server; reuses a dump (default the latest, `out\latest.txt`) |
| `-Pass gate\|auto\|eras\|obtain` | only the gate, only auto generation, or only the era rule (default, all three); `obtain` = the obtain audit (with `-Tier obtain` it's the only step; also leaves `report-<tier>.md`) |
| `-Dimension all\|<id>` | dimension where the factory is; `all` (default) goes through the tier's `contexts` (Overworld, `grindless:flat`, `grindless:void`) and gives an overall verdict |
| `-Explain <text>` / `-Detail` | full derivation of targets containing the text / of all of them |
| `-NodeExe <path>` | Node ≥ 18; if missing it looks for `$env:GG_NODE`, PATH, `.work\node`, and, failing that, downloads a portable Node LTS (official zip, with SHA-256) |
| `-Table [-TableFile <file>]` | (obtain) regenerates the pack's hidden table, `pack\kubejs\data\grindless\tables\hidden_until.json` by default, from the dump: **one command** after an era lands or a dump changes what is obtainable. The step's hiding check still compares against the dump's own tags, so it only agrees after a new dump with the new table |
| `-Implemented <era>` | (obtain) era up to which the pack is implemented (`IMPLEMENTED_ERA` in `integration/hidden.js`); defaults to the dump's `info.json` |

Analysis only, by hand: `node tools\analysis\reachability.mjs --tier mv --dump <folder> [--dimension <id>|all] [--pass gate|auto|eras] [--explain text] [--json output.json] [--quiet]`; the audit: `node tools\analysis\reachability.mjs --pass obtain --dump <folder> [--md report.md] [--json output.json] [--table hidden_until.json] [--implemented <era>] [--quiet]`.
Regenerating the hidden table from a dump (single command): `powershell -NoProfile -ExecutionPolicy Bypass -File tools\analysis\Invoke-Reachability.ps1 -Tier obtain -SkipDump -DumpDir <dump> -Table`.
Tests for the validator itself: `node --test --test-concurrency=1 "tools/analysis/test/*.test.mjs"` (a directory argument fails; use the glob), or `node tools\analysis\test\run.mjs`.

## The dump (`tools/test/overlay/kubejs/server_scripts/gg_dump.js`)

Only in the test overlay, never in the pack. Writes to `kubejs/exported/`:

- `recipes.json`: every final recipe with its raw JSON (`a:1` = added by a script); `tags.json`: members of every tag a recipe uses, plus a few fixed ones (including `c:hidden_from_recipe_viewers`, what the pack hides in EMI); `items.json`: registered items and fluids.
- `machines.json`: GT machines and their recipe types; `veins.json`: ore veins by layer and dimension.
- `fluid_veins.json`: GTM's fluid rig deposits (fluid, weight, yields, and dimensions where they can appear; `dims: null` = all).
- `config.json`: GTM config switches that decide progression (`worldgen.oreVeins.infiniteBedrockOresFluids`, `machines.enableMaintenance`, `machines.doBedrockOres`, `gameplay.hazardsEnabled`, `compat.energy.enableFEConverters`). What can't be read stays `null`: the analysis never assumes a default value.
- `structures.json`: data description of the pack's multiblock patterns (`global.grindless.structures` from `lib/patterns.js`); `info.json`.

Log markers: `GGTEST|dump|COLLECTED|READY|STRUCTURES|DONE|FAIL`.

## How it reasons

- **Resources**: items (`gtceu:coke_gem`), fluids (`fluid:gtceu:steam`), built machine (`m:<id>`), and running machine (`run:<id>` = built + what it consumes while operating). A recipe slot is met by any alternative (tag members).
- **Capital** (not consumed; having it once is enough): sample, tool, multiblock part, adjacent fluid (`chance 0`). **Catalyst**: chance-based consumption (the drill bit).
- **Machines**: a recipe only applies if there's a tier machine that accepts its type, its EU/t (`maxEUt`), and its temperature (`ebf_temp` against the coils). **Family tier veto** (`lib/model.mjs`, as `rules.recipeTier`/`isAboveTier` in `lv/multis.js`): a family recipe is filed under `<type>/<tier>/`; a machine with `vetoAbove: <tier>` (the LV, MV and HV drills and greenhouses, the sealed dome) skips the recipes filed above its tier, one with `onlyTier: <tier>` (the EV tripod) runs only that folder, and `onlyTier: ""` only the recipes with no tier folder (the steam drill and greenhouse, `steam/machines.js`, since 2026-10-25). `onlyRecipes: [id globs]` narrows a machine to its own recipes when two share a type and a folder (IV's pressurized drill takes `…/iv/pressurized_*`, the Mercury drill `…/iv/mercury_*`).
- **Step 1**: minimum fixed point from the world. PASS/FAIL per target; a FAIL carries the **minimum blocking chain** and the missing roots (no recipe, hand-only, nonexistent machine, empty tag, a deposit that doesn't allow the dimension...). **Gate dependencies and leaks**: a target with `without` recomputes scope without those rules (`build:<machine>`, `operate:<machine>`, `world:<id>`, `synthetic:<id>`, or a recipe id; globs, and an `@` variant needs a `*`: `build:gtceu:vacuum_freezer*`); with `expect:"unreachable"` it's a check that something ONLY comes out that way ("without the cleanroom there's no titanium", "the ender eye only comes from GT's chemical bath: if the vanilla recipe stays, LEAK").
- **Step 2**: "sustained" = a well-founded derivation from sources that consume nothing (drill, greenhouse, pump, crusher, fluid rig), where only machine fuel and catalysts can close the loop (steam → drill → coal → boiler → steam; the bit comes from bronze, which comes from drilling). Cycles with no source (compress ↔ decompress) don't count. States: sustained (PASS), finite (WARN: runs out), bootstrap only, hand-only, impossible.
- **Energy**: abstract keys `eu:lv`, `eu:mv`, `eu:hv`, `eu:ev`, `eu:iv`, `eu:luv` (given by the tier's turbines, generators, solar array and transformers) and `ae:power`; a generator of the pack's own recipe type (IV's fission reactor, Venus heat engine, Mercury solar field, the RTG) is read from its recipes (synthetic `recipesOf`): one rule per recipe, with its machine, fuel and site; no cables, amperage or dimension (power reaches the Moon and Mars through the AE2 bridge). **A multiblock's voltage** (GTM 7.5.3, `WorkableElectricMultiblockMachine.getMaxVoltage`): with 2 or more energy hatches of the highest tier it counts one step higher (V[tier+1]), regardless of amperage; the recipe fits if its voltage tier is ≤ the machine's. `energy: {voltage, hatches?}` computes it: two LV hatches = 128 V (MV), two MV = 512 V (HV); `hatches` comes from the pattern (`structures.json`) in the pack's multiblocks, and is declared for GTM's. Single-block machines (`gtceu:lv_*`, `gtceu:mv_*`) stay at their tier's voltage. **EBF**: `coilTemp` (cupronickel 1800 K, Kanthal 2700 K) + 100 K per tier above MV.
- **Dimension**: the factory is in a single dimension (`dimension`, default Overworld). A recipe with a dimension condition only applies where it says, and fluid deposits only count if their filter allows that dimension. A base outside the factory (the Moon from HV on, Mars from EV on) is declared with `conditions.dimension.asKeysFor: [ids]`: a recipe for that dimension needs the `dim:<id>` key (capital), given by a tier rule (the trip's synthetic: `moon-trip`, `mars-trip`), instead of being compared against the factory's dimension. A recipe's dimension conditions are ORed, as in GTM: one valid on the Moon or Mars needs either key. IV adds Venus and Mercury (synthetic `inner-trip`: the tier 3 rocket and the thermal suit) and the End (`end-trip`: the End's key; the leach field only runs there). GTM's altitude condition (`pos_y`, Venus's gas collector) is ignored: a source with it is met on its planet by building at that height.
- **Research** (IV): the scanner's data stick carries a `research:<id>` key (`normalize.mjs` reads its `assembly_line_research` NBT), and with `conditions.research.researchKeys` a recipe with a research condition (the assembly line's) needs that key, as capital: scanned once.
- **Eras** (step 3, `lib/eras.mjs`): for every item of era E, the gate is recomputed with every resource from eras later than E removed: no rule gives their keys (a recipe that gave them as a byproduct still gives the rest) and no world fact does either, and the world sources in their dimensions (the trip's `world:` rule) and recipes that only apply there are switched off. If the item is buildable with everything but not without them, that's a **violation**, and it carries the shortest blocking chain to the resource pulling on it (`✗ resource from a later era: titanium (ev)` or `✗ only comes from minecraft:the_end`). An era's output (the EV hull that HV builds as its gate) belongs to the next era. Generator rules copied from recipes that only run in a later era's dimension are switched off with them. Sibling substages (`eraSiblings`, IV's Venus and Mercury: one trip reaches both) are each later than the other, so neither may need the other's resources. A resource with `onlyFrom` adds **exclusivity** ("titanium only comes from the Moon"): without those resources none of its keys are reached; if any comes out, LEAK with the sources it enters through, grouped by the key they bring in (recycling what already carries it doesn't count as a source).

## Configuration (`tiers/<tier>.json`)

- **Base**: `unconditionalTypes` (crafting and world transformations, e.g. `ae2:transform`: always), `typeAliases`, `ignoreTypes` (globs), `toolTags`, `fluidContainers`, `conditions` (`adjacent_fluid`; `research`, `environmental_hazard`, and `ae2_circumstance_explosion` can't be met —`research` can from IV on, with `{"researchKeys": true}`: the scanner's `research:<id>` key—; `cleanroom` can't either until HV; everything else is ignored; a numeric condition with a cap, `{"field":..,"max":..}`, discards recipes that need more; `{"needs":[..]}` or `{"needsByField":{"field":"cleanroom","map":{"cleanroom":["run:gtceu:cleanroom"]}}}` meet it with a built machine or part —once, it's capital—, and a variant with no entry in the map still isn't supported), `contexts` (dimensions `--dimension all` goes through).
- **`world[]`** (what the world gives): `mode` `manual`|`auto`, `bootstrap`, `via` (the machine that resupplies it), `finite`, `enabled:false`, `items`, `template`+`fromVeins` (ores from the vein registry; each ore's item is resolved with the dump's registry —the material's namespace, `gtceu:`, vanilla, or another mod: `gtca:raw_germanite`, `minecraft:raw_iron`—, `overrides:{material:id}` is only a fallback; `fromVeins.requireRecipe: {type, input}` with `{id}` keeps only the veins the drill's table offers —some recipe of that type takes its sample—, and `fromVeins.requireItem`, looser, keeps the ones with the item: doesn't work when the pack sets a vein aside and leaves its sample registered, hidden, and recipe-less), `needs:[item]` (a manual gathering that first requires a built item, the End's key, or a key, the trip to the Moon `dim:gcyr:luna`: becomes a `world:<id>` rule, not a fact; its ores count as bootstrap —a trip—, never as a resupplied resource), `dimensions` (only in those), `origin` (where it's gathered, for the era rule; defaults to `fromVeins`'s dimensions), `requires:[{config,equals}]` (only if GTM's config has that value), `sustainedIf:{config,equals}` (otherwise the source runs out: WARN), and `fromFluidVeins` (`true` or `{fluids:[..]}`: fluids from `fluid_veins.json`'s deposits that allow the dimension).
- **`machines[]`**: `machine`, `id` (variant: the same item with different energy or a different coil), `types`, `maxEUt`, `needs`, `parts` (a part can be `{anyOf:[..], onlyIf:{config,equals}}`: only required with that GTM config value, e.g. the maintenance hatch with `machines.enableMaintenance`; if the config can't be read it's still required), `partsFromStructure`, `partAbilities` (this machine's own, overriding the tier's key by key), `requireAbilities: [ability]` (a variant built with an optional part its pattern offers: IV-B6's plants with the IV parallel hatch, `gtceu:hot_cell@parallel`; it warns if the pattern has no such part), `energy`, `coilTemp`, `vetoAbove`/`onlyTier` (the family tier veto, above), `onlyRecipes` (the machine's recipe allowlist, above), `optional` (a machine that may not be registered yet, such as another package's before its merge: no registry or structure warning, and its targets should be `optional` too). `machinesFromRegistry[]`: every single-block machine with a prefix (`gtceu:mv_`) and its `maxEUt`. `partAbilities`: which items satisfy each part of a pattern (`energy_input` → LV and MV hatches...). `synthetic[]`: boilers, transformers, generators, `ae:power`: rules that aren't recipes (`consumes`, `capital`, `produces`, `fuelOf`; `recipesOf: [types]` with optional `recipe: [id globs]` copies each recipe of a generator type into one rule, with its machine, inputs and conditions).
- **`targets[]` and `autoTargets[]`**: `item`|`fluid`|`anyOf`|`allOf`|`kind:"recipe"` with `type`, `output`, `input` (an id or a list: the recipe must have them all), and `dimension`. Options: `without:["synthetic:boiler-solar"]` (in auto, sustain itself without those rules; in the gate, be reached without them; globs over their names), `allowFinite:true`, `optional:true` (if it fails, WARN, and it doesn't sink the verdict), `expect:"unreachable"` (in `targets`, a leak check: PASS if it's NOT obtained in this tier, with or without `without`), or `expect:"not-automatic"` (in `autoTargets`: PASS if no machine resupplies it on its own). **Site checks** (`kind:"site"`, static: the same in every pass, whether or not the recipes can be completed): every recipe of `type`/`types` and/or with an id matching `recipe` (globs) carries dimension conditions, all of them among `dimensions`, and no reversed one; `exact:true` asks each recipe to name every dimension (the fuels' five air dimensions), and `allowAnywhere:[id globs]` lets some carry none (fuels with their own oxidizer). It checks rules like "every recipe of the regolith cell only runs on the Moon"; with no matching recipe it FAILs. `targetsFromVeins[]`/`autoTargetsFromVeins[]` generate one target per registry vein (`{id}` = the vein's id with the `_vein` chunk stripped; `requireRecipe: {type: "gtceu:vein_drilling", input: "grindless:vein_sample_{id}"}` skips veins the drill's table doesn't offer —no drilling recipe takes its sample: from other mods, set aside in `veins_excluded.json`, or waiting for their era— and the report lists them; `requireItem` only checks that the item exists).
- **Inheritance**: `extends` inherits from another tier (lists and maps are added together; a child element with the same id replaces the parent's), `inheritTargets` also inherits its targets (regression), and `dropTargets:[ids]` removes the ones that no longer apply (an LV leak that stops being one in MV) and the `eraItems` groups that no longer apply.
- **Era rule** (always inherited; in `eraResources` and `eraItems`, a child element with the same id is **merged field by field** with the parent's, so `{"id": "end", "era": "mv"}` moves a resource's era without repeating it; a new element with no `era` belongs to the era of the file that declares it):
  - `eraOrder`: the order of eras (`steam`, `lv`, `mv`, `hv`, `ev`, `ev-mars`, `iv`, `iv-venus`, `iv-mercury`, `luv`… up to `max`); declared by `steam.json`. `ev-mars` is EV's second substage (Mars, reached at the end of EV): what Mars brings (tungsten, samarium, merrillite, the ice) belongs to it, so nothing of the Moon substage (`ev`), the way to Mars included, may need it. IV has three: `iv` (home: the nuclear line), `iv-venus` and `iv-mercury`, which `eraSiblings: [["iv-venus", "iv-mercury"]]` declares siblings (one trip reaches both: neither may need the other).
  - `eraResources[]`: what each era brings. `{id, era, label, items?, exclude?, dimensions?, onlyFrom?, note}`. `items` are globs over item and fluid keys (`gtceu:*titanium*`, `fluid:gtceu:*titanium*`): those keys are removed from every source, including alloys and tools that carry them in their name. `dimensions` removes the world sources gathered there (the `world` entry's `origin`, or its `fromVeins`'s dimensions) and recipes conditioned on that dimension. `onlyFrom: [resource ids]` turns on exclusivity.
  - `eraItems[]`: what belongs to each era. `{id, era, label, items?, exclude?, inputsOf?, optional?, note}`. `items` are ids or globs over the registry (items, `fluid:`) and built machines (`m:<id>` = formed multiblock). In a glob, something that already belongs to a later resource (`gtceu:hv_titanium_drill`, the HV tool with a titanium head) doesn't count as this era's and is listed separately; an explicit id does count. `inputsOf: [recipe id globs]` turns every input of those recipes into an era item (met by any of its alternatives): the bit and the samples of `grindless:vein_drilling/hv/*`. `optional`: if it fails, WARN. An explicit item that isn't made even with every resource gives WARN (the rule can't be checked) with its chain; one that doesn't exist in the registry gives FAIL (WARN if the group is optional).
- **Next version** (`tiers/next/`): prepared, not-yet-active layers. `tiers/next/<tier>.json` inherits from the current one by path (`"extends": "../hv"`), and while a layer is being analyzed, every `extends` by name in the chain is looked up in `tiers/next/` first: `next/hv` → `hv` → `next/mv` → `mv` → `lv` → `steam`. It's run on purpose (`-Tier next/hv`); the day the pack carries the change, each layer gets merged into its tier and deleted. None exist today: v0.5.0 merged the End's into MV and the Moon's into `mv.json` and `hv.json`.
- **The pack's multiblocks**: with `partsFromStructure:true` parts come from `structures.json` (casing with a minimum, ability-based parts, frames, piping), translated with `partAbilities`; `parts` stays as a fallback, and the analysis warns if the dump has no structure for it. In an "or" cell, options with a minimum are mandatory and the others are only needed when the mandatory ones can't fill every cell: a casing with a minimum and no maximum fills the rest, so an optional part next to it (a spare hatch, the parallel hatch) stays optional (before IV-B6 it was counted as required). **AE2**: `ae2:inscriber`, `ae2:charger`, and `ae2:transform` are read as recipes; the inscriber and charger need `ae:power`.

## Obtain audit (`--pass obtain`)

What is **never** obtained, in any era: starts from every source the pack has today and every recipe of any tier, and lists the GT-stack items and fluids that are never reached, grouped by material, with the recipes that need or give them (what's seen in EMI without being craftable). Every group is classified: **A** deserves a source (opens a line or an automation), **B** arrives with a later era from `docs/journey.md` (hide until then), **C** will never arrive (hide the item and its recipes).

- **Run**: `Invoke-Reachability.ps1 -Tier obtain -SkipDump -DumpDir <dump>` (leaves `report-obtain.txt/.json/.md`) or `node tools\analysis\reachability.mjs --pass obtain --dump <dump> --md report.md [--table <table>] [--implemented <era>]`. Config: `tiers/obtain.json` (inherits recipe types, aliases, tools, boilers, and steam machines from `steam`; `--pass obtain` uses it if the requested tier has no `obtain` section). Exit `0` if everything is classified and the pack's hiding matches; `1` if there are "?" groups, something hidden that's obtainable, or something that should be hidden and is visible.
- **Sources** (`lib/obtain.mjs`, over the same `buildModel`): the drills' table veins (`veins.requireRecipe`: one or a list, e.g. `gtceu:vein_drilling`, the lunar drill `gtceu:lunar_drilling` and, since IV, the leach field `gtceu:in_situ_leaching`, each with its recipe type) in `reachableDimensions` (Overworld, Nether, End, Flat, Void, and, since v0.5.0, the Moon, since v0.6.0, Mars and, since IV, Venus and Mercury); weighted fluid deposits (via the fluid rig); `world` (rubber, marble, and red granite trees, the Moon's, Mars', Venus' and Mercury's ground, the coal pile, the special-recipe facade); and everything in the unaudited namespaces (vanilla, decoration, AE2, Productive Bees...) except `notFree` (generation eggs, creative, technical blocks). `ignoreNamespaces` (Create) neither gives nor is listed.
- **Recipes**: all of them. Every registry machine (`machinesFromRegistry` with `maxEUtByTier`: each single-block one runs up to its tier's voltage; multiblocks are uncapped; `includeTypeless` to use typeless ones in `via`); energy, parts, the clean room, and research are assumed obtainable; GT-less types (crafting, furnace, other mods) need no machine; conditions are ignored except dimension, which needs the `dim:<id>` key (a fact for every reachable dimension); buckets fill and empty with no recipe.
- **Bees** (`bees`, on by default): `nbtTyped` tells apart honeycombs, honeycomb blocks, and configurable eggs by their type (`EntityTag.type`, as an object, SNBT, or JSON). Hive, breeding, conversion, nests, and fishing are rules over `bee:<id>` keys; an egg gives its bee, and the incubator gives the egg of a bee you already have (with a chicken egg); the vanilla bee is a world fact.
- **Audited**: items and fluids from `audit` (gtceu, gtca, gtnn, gcyr, grindless, and GT's addons), minus `flowing_` ones, minus `ignore`, and, with `ignoreOreBlocks`, minus ore blocks (they're world blocks; crushed, washed, and purified forms do count).
- **Groups**: every item goes to the longest material whose name it carries, if the rest of the id is form words (dust, ingot, plate, wire, pipe, tool, bucket, molten, plasma...); machines and parts go alone. "Loose forms" = the material is obtained, but those forms aren't.
- **Hints**: recipes that need it (a slot with no reachable alternative) and that give it; what the ones that need it give (whether it's already obtained or not); and, for A and "?", what it would unlock (a pass with its forms as facts, without recycling its own forms).
- **Later stages** (`later[]`, in order and cumulative): `{id, era, until, label, dimensions?, veins?, materials?, items?}`. A dimension adds all its veins and its recipes conditioned on that dimension; `veins` adds specific veins (the End's, set aside in `veins_excluded.json`); `materials` adds the raw ores of standalone vein materials (a vein the pack has already removed from the world, like scheelite's, doesn't appear in veins.json); `items` adds items of the place (a planet's ground; globs, no ore blocks). What a stage obtains is **automatic B** with that era; `until` is the id of the era when the place is reached, the one the hidden table uses. A place already reached (the Moon, HV; Mars, EV; Venus, Mercury and the End's pitchblende, IV) isn't a stage: it goes in `reachableDimensions` (or, for a vein, in the table the drills and the leach field offer). A group goes to the **first** stage that reaches it, so the order names the cause (until IV, the End's pitchblende vein went before Venus' naquadah one, because the naquadah vein's plutonium ore also gives uraninite). Since IV the only stage left is Proxima b (`uhv`).
- **Classification** (`classes[]`: `{class, materials?, items?, partial?, forms?: "ore", fallback?, reason, era?, until?, keepRecipes?, source?}`, globs over the group's id and its items): first the A and B rules, then `creative` (C), then the later era (automatic B), then the C rules, and last the fallback ones. A C never covers up a later era: what arrives with an era isn't "never". `partial`/`forms: "ore"` filter by loose forms and by ore forms. Every B carries `until` (a B rule without it warns). `keepRecipes` (on a C): its recipes stay, on the server and in EMI (old items from earlier versions and their conversion into the new one). Whatever no rule classifies is "?" (FAIL: a new material nobody has looked at); rules that classify nothing anymore show up in the report.
- **Hidden table** (`--table pack\kubejs\data\grindless\tables\hidden_until.json`): one group per line, `{material, until, reason, items, fluids, removeRecipes?, keepRecipes?}`: B's with their `until`, and C's with `"never"` and `removeRecipes`, the recipes that only exist for them (a slot that only accepts C items, or every output being C; a C output next to a B isn't enough). It's merged with the existing table: it keeps the recipes already removed from groups that are still C (a dump made with the active table no longer brings them). It isn't hand-edited: `tiers/obtain.json` is changed and it's regenerated.
- **In the pack**: `server_scripts/grindless/integration/hidden.js` reads the table. Every group with `until` above its `IMPLEMENTED_ERA` constant (today `iv`) or `"never"` goes into two item/fluid tags: `c:hidden_from_recipe_viewers` (EMI drops it from its index) and `grindless:hidden_with_recipes` (`assets/emi/index/stacks/grindless_hidden_with_recipes.json` disables it in EMI, which only reads its data in the `emi` namespace: every recipe that needs it, gives it, or uses it as a catalyst also disappears). `keepRecipes` groups only get the first tag. C's `removeRecipes` are removed from the server (the datapack's by id, and the ones the pack's own scripts add, from `event.addedRecipes`). Nothing is unregistered. When an era lands, `IMPLEMENTED_ERA` is bumped (and the era enters the config's `reachableDimensions`/`later`) and the table is regenerated (`Invoke-Reachability.ps1 -Tier obtain -SkipDump -DumpDir <dump> -Table`). JEI runs under EMI (JEMI): it has no list of its own to hide from. Tests: `overlay/kubejs/server_scripts/gg_test_hidden.js` (server) and `client_scripts/gg_test_hidden.js` (the real EMI and JEI, with a marker).
- **Hiding vs. the audit**: if the dump carries `c:hidden_from_recipe_viewers` (items and fluids), the step says how many forms of each group are hidden and fails if something obtainable is hidden. If it also knows up to which era the pack is implemented (`info.json` → `hidden.implementedEra`, which gg_dump dumps from `global.grindless.hidden`, or `--implemented <era>`), it also fails if something C or a later B is visible (the table is stale: regenerate it), and if a B group's era is already implemented while the group is still unobtained (`landed`: the era arrived without it, so its rule must be reclassified —C, or a later era— or it needs a source).
- **Limits**: other mods' content is assumed obtainable; so are parts, energy, and conditions (it may say "obtained" too often). A source the model doesn't know (a world mechanic with no recipe) gives one extra "never": add it to `world`. Planets only count their veins, their ground, and their recipes conditioned on that dimension.

## Limits

- Qualitative: ignores quantities, times, and yields; a chance-based output counts as produced. It says production *exists* and sustains itself, not that it *covers* consumption. GTM's brine deposit only appears in oceans and isn't counted.
- Multiblock parts that are NOT the pack's own (coke oven, PBF, primitive pump, EBF, pyrolysis, fluid rig...) are hand-copied into `machines[].parts`; the pack's own come from `structures.json`. The validator warns if an id doesn't exist, not if a GTM pattern changed. Only the multiblocks each tier declares are from GTM (HV adds the cleanroom, vacuum freezer, cracker, distillation tower, and large chemical reactor with 2 MV hatches, and the Kanthal EBF with 2 HV): the rest's recipes (implosion compressor, vacuum alloy furnaces, large boilers...) count as "no machine" (out of caution: it may give one extra FAIL, never one extra PASS). The pack's own multiblocks are modeled with their design's HV hatch even if their pattern allows any tier.
- The world is an honest but manual list: no mob loot (`enabled:false`) and no vanilla ores (GTM removes them; they come from GT's veins).
- The family's tier folders are modeled (`vetoAbove`/`onlyTier`), but not the machines' other per-recipe preferences (a drill with drilling fluid in its hatch prefers the fluid recipes, a greenhouse's fertilizer mode, the cryogenic plant's night price): any machine with the input, the energy and the folder "can" run a recipe. To check that a specific machine does the job, the target switches the others off with `without:["operate:gtceu:steam_vein_drill", …]` (this is how the HV drill and HV greenhouse are checked).
- Recycling recipes GT injects at runtime aren't included, nor are `ae2:entropy`/`matter_cannon`/`facade`. Cables, hatches, and amperage aren't modeled: whether an MV grid holds 4 A, or whether the 16 generators fit, isn't checked.
- Recipe conditions are ignored except `conditions`'s; dimension is checked on every recipe with a dimension condition.
- Era rule: material resources are recognized by the key's **name** (globs); something that carries the material without naming it is only cut off if it's made from it. A dimension resource removes the world sources gathered there and the recipes that only apply there; it doesn't infer which materials are exclusive to that dimension. It checks that the item *can be made* (as in the gate), not that it's sustained. Productive Bees' configurable honeycombs aren't a source in the tiers' model (their hives have no machine; the obtain audit does model bees), so a bee-based leak isn't seen. The trip to the End's source only counts veins the drill's table offers (with drilling recipes): a vein the pack sets aside but that still generates in the world (today, scheelite's) isn't seen as a leak.
- IV: GTM's IV energy and dynamo hatches wait for Mercury (the IV voltage coil takes fine iridium wire), so before Mercury our IV multiblocks are modeled on 2 EV hatches (IV voltage) and IV's generators on EV dynamos (stepped up by the EV→IV transformer); `eu:ev` stands for both. GTM's multiblocks that GCYM or the IV-B6 split don't name (the large mixer, the mega furnace and freezer) aren't modeled, nor are GTCA's megas and GT--'s Maceration Stack (their types already run in IV's single blocks and GTM's large chemical reactor). The parallel hatch's copies, the assembly line's ordered inputs and its feeding from AE2 aren't modeled either (quantities and logistics, proven on IV-B6's bench): only that a variant needs the hatch and the line needs its research. GT--'s neutron activator isn't a modeled machine (its controller isn't reachable in IV: a check says so), so until IV-B3's naquadah plant the naquadah ingot and the UHPIC wafer are optional targets (WARN).
