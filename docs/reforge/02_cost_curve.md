# Reforge 02: cost-curve mechanism (RF-2A)

Phase 2 raises the cost of key items on a curve (DECISIONS.md:708: core index about 3 x 2.5^n from MV, n = 0 at MV). This package is the mechanism and its tooling only. **Every table lands disabled (factor 1.0), so the recipe set is unchanged.** Later Phase 2 packages switch bands on by editing a table; nobody edits recipes by hand.

## Mechanism

`pack/kubejs/server_scripts/grindless/integration/cost_curve.js` runs once in `ServerEvents.recipes` and scales the **consumed item and fluid inputs** of the GT machine recipes that make key items (GTM originals and ours) by `ceil(n x factor)`. Never touched: outputs, chances, duration, EU/t, tick inputs, non-consumed inputs (chance 0 or below max), programmed circuits, research data. Amounts cap at INT_MAX.

`tools/analysis/lib/cost_curve.mjs` loads the very same `cost_curve.js` (stubbed `global`), so `cost-matrix`, `capacity-lint` and `kubejs_static.mjs` run the pack's rule, not a copy; `cost-curve.test.mjs` proves parity.

### Table schema

`pack/kubejs/data/grindless/tables/cost_curve/<era>.json`, one per era `mv hv ev iv luv zpm uv uhv uev uiv uxv opv max` (LV is review-only, no table; MAX+ is documentation only).

```json
{ "era": "mv", "enabled": false, "item": 1, "fluid": 1,
  "keys":    ["gtceu:mv_electric_motor", "gtceu:good_*"],
  "include": ["gtceu:assembler/*_mv_*"],
  "exclude": ["gtceu:assembler/example_artefact"],
  "remove":  ["gtceu:shaped/electric_motor_mv"],
  "override": {"gtceu:macerator/*": "none"} }
```

- `enabled` false: the table is read and validated, nothing changes. `item` / `fluid` are factors (>= 1).
- `keys` (ids or `*` globs): a recipe belongs to the era whose table lists its **primary output** (first item output). Generated by `cost-matrix --write-tables`.
- `include`: recipe-id globs for recipes whose output is not a key; their era is the tier of their EU/t (MV and above only).
- `override {glob: era|"none"}` moves a selected recipe to another era or drops it; `exclude` drops by glob (artefacts of the matrix, with a reason in the commit).
- `remove`: recipe ids deleted when the table is enabled (a bypass such as a crafting-table shortcut). Never used for a route fix that needs a new recipe.

### Selection rule (one rule, `makeSelector`)

1. Only GT machine recipes: type `gtceu:*` with an `inputs` object.
2. Era = era of the primary output via `keys`; else the table whose `include` matches, by EU/t tier; `override` / `exclude` last.
3. Disabled tables leave their recipes alone; `remove` applies only to enabled tables.

**Added recipes report `type: "unknown"` in their JSON** (also after `serialize()`; the real type is only the `[<type>]` suffix of `String(r)`). The pass therefore takes the type from the event (`typeOfAdded`) and the Node side from the dump's `t` field. Without this, every recipe of ours is skipped (found in the first solver run; regression test in `cost-curve.test.mjs`).

### Originals versus added recipes (the open question, settled from source)

Question: can a recipes event change GTM's recipe inputs in place?

**Yes for originals; added recipes need a different path.** Evidence (KubeJS 2001 `recipe/`, GTM v7.5.3):

- `RecipesEventJS.java:556` `forEachRecipe` visits original recipes only; `:380-392` the final build; `:176-177` originals map versus the concurrent `addedRecipes`.
- `RecipeJS.java`: `json` is public, `save()` sets `changed`, and `createRecipe()` re-serializes only when `newRecipe || hasChanged()`. `RecipeSchema.deserialize(false)` gives originals no write flags, so editing `r.json` and calling `save()` survives into the live recipe. GTM's `integration/kjs/recipe/GTRecipeSchema.java:1361-1365` and `components/CapabilityMapComponent.java:57-84` define the `inputs` JSON the pass writes; edits skip the lossy GT component round trip. `power/generators.js:~210-250` already edits originals in place.
- Added recipes hold write-flag holders: direct JSON edits are overwritten when the event ends. The pass does `serialize()`, `set('inputs', ...)`, `serialize()` and verifies the amounts. Fallback if a future KubeJS breaks this: remove from `addedRecipes` and re-add through `event.custom(json).id(id)` (as `hidden.js:161-163`).

Confirmed live by the T1 run below (both paths, exact amounts).

### Script order: the -300 band

`tools/analysis/script_order.json` gains `"server_scripts/grindless/integration/cost_curve.js": -300`. The pass must see every recipe that other scripts add, remove or derive, so it sits **after** every pack recipe script (`hidden.js` at -100, the -200 era scripts) and **before** `gg_dump.js` (-100000), whose dump must show the scaled recipes. The integrator stamps the `// priority:` header with `script-order.mjs --write` at merge; this package neither stamps nor commits a header. For T1 the bench copy carried `// priority: -99999`.

## Solved factors (proposal)

`cost-matrix --dump <dump> --solve` iterates a log-log secant per era, from MV upward, with the previous eras' factors applied (item and fluid equal, `fluidFactorRatio` 1). It stops on a plateau (index gain under 2%) or at `maxFactor` 4096, and prints the three least-grown core groups instead of an absurd factor.

**First run, nothing removed:** MV hits a plateau at index 2.39 (factor 59), HV needs 301, EV 641, IV 4,096, and the capacity lint reports 74 new overflows (rubber 12-170 million mB per recipe). Cause: the **crafting-table `gtceu:shaped/*` recipes of the core components** (hull, motor, pump, piston, conveyor, robot arm, emitter, sensor, field generator at MV to IV) are not machine recipes, so the pass cannot scale them, and the matrix picks them as the cheapest route (growth x1.1 to x1.6 for every x59). That is a **bypass**, not a reason for a bigger factor.

Predicted capacity overflows at these factors (`capacity-lint --dump <dump> --table <tables> --factors <solved.json>`): errors 138 before, 144 after. **Six new overflows**, all one family: `gtnn:component_assembly_line/conveyor_module_{mv,hv}_{rubber,silicone_rubber,styrene_butadiene_rubber}` (rubber 78,300 mB against a 64,000 mB MV tank; 141,876 against 128,000 at HV; all six exceed their tank). Fix when the MV and HV bands land: `exclude` or `override` those recipes and give the conveyor a rubber route that is not one mega-input (a second tank stage), not a lower factor. New multiblock-only warnings: IV 15, LuV 10, ZPM 8, EV 6, OPV 1.

For comparison the unremoved run (first run above) predicts 212 errors after (74 new): MV 9, HV 14, EV 25, IV 26.

## Phase 2 route-fix list (real shortcuts, not excluded)

`--trace` on the three named cases:

- **`gtceu:shaped/tiny_dust_*` splitting**: an artefact of the shaped-count defect above (fixed in the matrix, no `excludeRecipes` entry needed).
- **`gtceu:centrifuge/ash_separation`**: real. It yields hematite at 0.0275 per ash; ash comes from `grindless:syngas/hv/gasify_carbon` (0.111 per carbon), carbon from `electrolyzer/diamond_electrolysis` (one diamond dust to 64 carbon) and diamond from `grindless:diamond_cvd/nanodiamond` and `cvd_diamond`, which output net hydrogen: iron from gases. Route fix: diamond CVD must consume its carbon source at a rate that closes the loop, and the electrolysis must stop multiplying matter.
- **`netherrack_blue_topaz_ore`**: blue topaz ore is a base item consumed by four recipes, 51-63% of the ZPM+ capstones. Verify a scalable automatable route (vein drilling) at 10^4 scale before raising ZPM+.

Cheap bases that make costs collapse and need an honest route: hydrogen (~7e-9) via `electrolyzer/decomposition_electrolyzing_methane`; methane via `centrifuge/red_mushroom_separation`; oxygen via `decomposition_electrolyzing_nitrogen_dioxide` from `grindless:distillation_tower/offworld_only/distill_liquid_ender_air`; copper dust via `shaped/mortar_grind_copper`.

Bypasses in the solved output (`cost-matrix --solve` writes them to `solved.json`): MV 16, HV 6, EV 1, IV 6 after the removal above (mostly energy hatch, superconductor splitting, circuits and ours that are cheaper than the era median; none above the proposal's tolerance), LuV 4, ZPM 2, UV 1. Eras at factor 1.0 list every group as "not scaled", which is noise.

## Tooling

- `cost-matrix.mjs --table <dir> [--factors <f>]` predicts the pass on a dump; `--solve [--table <dir>] [--era <list>] [--factors <f>] --out <dir> --compare <csv>` proposes factors, `--write-tables <dir>` writes the tables with the keys of the matrix, `--trace` prints derivations.
- `capacity-lint.mjs --dump <dir> [--table <dir>] [--factors <f>] [--top N]` lints every dump recipe (GTM originals included) and reports new overflows per era.
- `kubejs_static.mjs` mirrors `ServerEvents.recipes` for the pass; the default T0 capacity ratchet (`capacity_known.json`) is unchanged: 87 known violations.
- One `--solve` takes 10 to 25 minutes (15 s per matrix run); run it in the background.
